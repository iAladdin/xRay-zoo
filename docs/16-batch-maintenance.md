# 批量节点维护

入口：管理员后台 → 区域节点 → 连接与维护。勾选节点或“全选可维护节点”，选择批量停止并回收、启动/重建、重连、重启或轮换 IP，检查对象与影响后提交。每批最多 50 台；已回收节点可勾选重建；有冲突任务的节点会被跳过，提交及执行时再次校验。

## 执行与结果

- 普通维护逐台执行，一台失败不阻断后续节点。“已提交”表示控制命令完成，是否恢复连接以节点最新检测状态为准；重启可能中断连接，不保证上一台恢复就绪后才处理下一台。
- 停用仍表示停止代理服务、移出新订阅配置；不会关闭或销毁 Azure VM，云资源继续计费。失败的停用期望由既有 worker 继续同步。
- IP 轮换在确认前逐台调用真实 Azure 预检，最多同时检查 2 台；只有通过且未过期的预览可提交。失败项显示原因并跳过。后续由既有轮换任务分配/绑定/验证/发布/释放 IP，原订阅 URL 保持不变。点击每行“查看 IP 轮换”处理重试或回滚。
- 后台记录每台节点的等待、执行中、已提交/完成、失败、跳过或结果待核实。窗口关闭、页面刷新不取消已经提交的任务。页面每 3 秒读取批次进度，节点状态仍按原 10 秒刷新。
- “重新处理未完成节点”只选择失败、跳过或待核实的普通项，重新展示确认；已经提交成功的项不重复执行。已有 IP 轮换任务的项必须在原任务中处理，避免另起一轮。批次完成后保留当时的执行结果，之后原 IP 任务的变化以任务详情为准。

## 恢复与幂等

`NodeMaintenanceBatch` 保存操作、节点快照、逐项结果、请求摘要和租约。`actorId + idempotencyKey` 唯一；重复提交同一请求返回原批次，同一个键改变对象或操作会拒绝。确认窗口在网络错误时保留原键。

worker 每约 5 秒从数据库重新发现运行中批次，复用单并发机器队列，每次处理一个普通节点动作或提交一个轮换任务。使用 5 分钟批次租约、30 秒续租，节点动作继续使用原有互斥锁，轮换中的节点不能再执行普通维护。

普通动作在发送控制命令前先写入“执行中”。若进程中断、未能保存结果，恢复后标记“结果待核实”，不会自动重复重启；管理员核实后可显式重新操作。轮换使用逐项稳定 UUID 作为幂等键，能恢复提交成功但响应丢失的原轮换任务。

所有接口仍要求 ADMIN 和写请求 Origin 校验。批次创建留审计记录，普通动作及 IP 轮换沿用逐节点审计。列表不返回预览快照、凭证、租约或资源管理密钥。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/admin/node-maintenance` | `{action,nodeIds,idempotencyKey,plans?}`；轮换附每个节点的 `{nodeId,planId}` |
| GET | `/admin/node-maintenance` | 全部运行中批次和最近 20 个已结束批次 |
| GET | `/admin/node-maintenance/:id` | 批次进度、计数和逐节点结果 |

## 验证

- `pnpm test:maintenance`：独立数据库 schema 与控制动作替身，验证参数边界、双击幂等、混合结果、状态变化、节点冲突、租约、崩溃后不重放、四种维护动作、IP 预览归属、丢失响应/进程中断恢复及公开字段过滤；不执行真实节点维护或 Azure 写入。
- 管理端 401/403、非法批量请求、单节点轮换与路由回归，以及 TypeScript/网页构建。
- 2026-11-18 浏览器验证全选 6 台、清空与选择 JP/SG 两台；实际批量重连两台成功提交，刷新后仍保留逐项结果，6/6 节点控制就绪。IP 轮换只验证批量只读预检和取消，未创建轮换任务或云资源；批量停用、重启及公网 IP 切换没有在现有业务上执行。

节点资源生命周期和按区域操作见[释放与重建](17-disposable-nodes.md)。原 enable/disable 仅为代理维护兼容接口，默认 UI 已使用 release/rebuild。
